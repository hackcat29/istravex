Toy indexers prove the corpus discriminates. A real indexer proves it's useful. The pilot runs [stellar/wallet-backend](https://github.com/stellar/wallet-backend), SDF's backend for wallets, over every fixture and scores the result.

## How it works

Nothing in wallet-backend is changed or mocked except the network:

<Steps>
  <Step title="Pinned checkout">
    wallet-backend is cloned into `.cache/wallet-backend` at commit [`3e22515`](https://github.com/stellar/wallet-backend/commit/3e22515a44979fdc3a558fda3991ca2b48e38cef) (main, 12 November 2026).
  </Step>
  <Step title="Adapter">
    A small Go file, `kit/pilot/wallet-backend/adapter.go`, is copied in behind a build tag. It needs the module's internal packages, which is why it lives inside the checkout.
  </Step>
  <Step title="Mock RPC">
    The [mock RPC](/tools/mock-rpc) serves the corpus's canonical ledgers, one server per network.
  </Step>
  <Step title="wallet-backend's own pipeline">
    For each fixture, the adapter builds wallet-backend's own RPC ledger backend (`ingest.NewLedgerBackend`), fetches the fixture's ledger through `getLedgers`, and runs `indexer.ProcessLedger`, the same per-ledger function live ingestion calls. It prints what the indexer produced for the fixture's transaction. Nothing is written to a database; the output is exactly what ingestion would hand to persistence.
  </Step>
  <Step title="Score">
    `kit/pilot/score.mjs` compares that output with each fixture's expectations, field by field.
  </Step>
  <Step title="Persistence, without a database">
    The adapter also runs every column encoder persistence would run on what it produced: each field's `driver.Valuer`, and the participants' `AddressBytea` keys. A value that can't be encoded, or two participants that encode to the same key, halts real ingestion at that ledger, so the scorer counts it as **dropped**.
  </Step>
  <Step title="Lint">
    `istravex-lint` runs over the same checkout, and each finding is matched against a reviewed triage in `kit/pilot/wallet-backend/triage.json`. An untriaged finding fails CI.
  </Step>
</Steps>

```bash
npm run pilot:wallet-backend   # → corpus/results/pilot-wallet-backend.json
```

Across every shape real traffic uses, wallet-backend charges fee-bump fees to the right account at the charged amount, keeps muxed IDs exact up to 2⁶⁴ − 1 (it stores `to_muxed_id` as text), records the full `P…` signer, indexes the SAC trustline from metadata, and keeps a muxed source's participant as its `G…` account. On every pattern in the corpus it indexes, it does what the [hardening guide](/guide/overview) asks.

## Before and after each upstream fix

Today's wallet-backend passing proves the corpus doesn't raise false alarms. It doesn't prove the corpus would have caught anything. So for each bug fixed upstream, the pilot checks out the commit **before** the fix and the fix **itself**, and runs the fixtures for that bug on both. The kit reproduces the bug when the commit before gets a fixture wrong and the fix gets every one right; for lint, when the expected rule fires before the fix and not after.

<Sightings />

What fails, before each fix:

- **#729**: the signed-payload signer's state change can't be encoded: `state_change.SignerAccountID … has a 68-byte key`. Real ingestion rolls back the ledger with the cursor and retries it forever.
- **#731**: the SAC trustline is recorded, but no `TRUSTLINE` state change is.
- **#716** (fixed by #753): the muxed source's `G…` and `M…` forms encode to the same participant key, the duplicate primary key that halted ingestion. IX003 flags the four call sites #753 changed.
- **9538b3c**: Soroban participants came from an unbounded recursion over the authorization tree. IX002 flags it; it's gone after the commit.

<Note>
The commits before these fixes use go-stellar-sdk 0.7.3, which predates protocol 29: it can't decode a protocol 29 ledger header (`StellarValueType 3`). They ran against protocol 28 networks, so the sightings replay a protocol 28 copy of the same scenarios, generated by the same pinned stellar-core (`node kit/capture/generate.mjs --protocol 28 --out .cache/corpus-p28`). The commits and fixtures are listed in [`kit/pilot/wallet-backend/refs.json`](https://github.com/hackcat29/istravex/blob/main/kit/pilot/wallet-backend/refs.json).
</Note>

## Lint

One finding, triaged **latent**:

```go internal/utils/ingestion_utils.go
switch memoType {
case xdr.MemoTypeMemoNone:
    return nil, memoType.String()
case xdr.MemoTypeMemoText:
    if text, ok := memo.GetText(); ok {   // IX001
        return &text, memoType.String()
    }
case xdr.MemoTypeMemoId:
```

`utils.Memo` returns memo text as a Go string without UTF-8 validation. Nothing outside tests calls it at this commit and no migration has a memo column, so it isn't reachable today. It's worth a guard before memos are stored. Because it isn't a live bug, no upstream issue was filed.

## What the pilot taught us about our own code

The first version of the pilot driver passed wallet-backend's JSON output through `JSON.parse` and reported muxed IDs off by a few hundred. wallet-backend was right. The driver was rounding them, the exact bug the corpus exists to catch. The adapter now emits every 64-bit integer as a string.
