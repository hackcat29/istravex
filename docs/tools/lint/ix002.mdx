## What it flags

Two shapes of walk over recursive XDR types (`ScVal`, `ScVec`, `ScMap`, `ScMapEntry`, `SorobanAuthorizedInvocation`, `SorobanAuthorizedFunction`):

1. **Recursion.** A function that takes one of these types, calls itself, and has no integer parameter that it compares against anything.
2. **Work lists.** A loop that pushes a node's children onto a slice it then pops from (`stack = append(stack, inv.SubInvocations...)`, or the elements of a vec or map), in a function that never compares a counter against a bound.

```go
func walk(v xdr.ScVal) int { // IX002: recursion, no depth limit
    n := 1
    if v.Vec != nil {
        for _, c := range **v.Vec {
            n += walk(c)
        }
    }
    return n
}

for len(stack) > 0 {
    inv := stack[len(stack)-1]
    stack = stack[:len(stack)-1]
    stack = append(stack, inv.SubInvocations...) // IX002: work list, no size limit
}
```

## Why it matters

stellar-core bounds neither the depth nor the width of an authorization tree or a contract value: only the transaction size does (132,096 bytes on mainnet). Decoders bound nesting when their limits are on, but a value built in memory, decoded with limits off, or merged from several sources can nest deeper than your walker expects. Recursion then overflows the stack; a work list grows the heap without bound. Either way, in an indexer it's a crash loop on one ledger.

## Fix

Carry a depth, count nodes, and stop past a bound. [Recommended limits](/guide/limits) derives the numbers: depth 100 (the host's own limit) and about 33,000 nodes per transaction.

```go
func walk(v xdr.ScVal, depth int, budget *int) error {
    if depth > 100 {
        return errTooDeep
    }
    if *budget--; *budget < 0 {
        return errTooLarge
    }
    // … recurse with depth+1
    return nil
}
```

Any ordered comparison of an integer parameter satisfies the recursion check; any ordered comparison of a counter satisfies the work-list check.

## In the wild

On wallet-backend, IX002 flags `participantsFromInvocationAndSubInvocations` (`internal/indexer/processors/contract_operations.go:53`) on every commit up to 28 September 2026: it collected Soroban participants by recursing over the authorization tree with no limit. Commit [9538b3c](https://github.com/stellar/wallet-backend/commit/9538b3caeaebfeb3d034146c0ce9643c3066cf8a) replaced it ("derive Soroban participants from executed meta, not the auth tree"), and IX002 is clean on main. The [pilot](/pilots/wallet-backend#before-and-after-each-upstream-fix) checks both commits on every run.
