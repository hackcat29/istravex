Each SDK gets a runner that reads the corpus and checks every fixture three ways: JavaScript (`@stellar/stellar-sdk`), Go (`go-stellar-sdk`), Rust (`stellar-xdr`), Python (`stellar-sdk`, and `stellar-xdr`, the package replacing its XDR module), Java (`java-stellar-sdk`) and PHP (`stellar-php-sdk`). The RFP asks for at least the first three; the rest are there because the same bugs travel between SDKs, and they did: the PHP and Java SDKs compute the same wrong hash for one class of mainnet transaction.

| Check | Question it answers |
|---|---|
| **decode** | Does every XDR value in the fixture parse as its declared type? |
| **reencode** | Does encoding the decoded value give back the exact original bytes? |
| **native** | Do the SDK's high-level forms, the ones applications actually use, produce the fixture's expected values? |

The third check is where real bugs live. Decoding and re-encoding are mechanical: the generated XDR code either handles a type or it doesn't. The high-level conversions (strkeys, muxed accounts, transaction hashes, amounts, asset ordering, native maps) are hand-written, and they're where a 64-bit ID quietly becomes a float.

Each native check has a name (`muxed_id`, `pool_id`, `native_keeps_every_entry`…) and runs on its own, so one failure doesn't hide the rest, and every failure in a result file says exactly which check and why.

**Bytes a decoder must refuse.** The [synthetic fixtures](/corpus/fixtures) hold encodings no network produces: 101 operations, a 29-byte memo, an `ScVal` claiming 2³² − 1 elements, a vector nested 2,000 deep. Their files are marked `expect: decode_error`, and a runner passes them when decoding **fails** cleanly. The Rust runner decodes untrusted input with `Limits { depth: 500, len: input.len() }`, the host's own depth; see [Recommended limits](/guide/limits).

## Results

<Sdks />

**The `tx` and `ledger` profiles.** The [set-cover fixtures](/corpus/cell-coverage) carry Horizon's values for their transaction or ledger. Every runner computes them from raw XDR: the transaction hash, outcome, source and fee payer, fee charged and maximum fee, operation types, memo type and signature count; or the ledger hash (the SHA-256 of the header), previous hash, protocol, fees, reserve, transaction count and close time. Python `stellar-xdr` and PHP run these profiles and every decode and re-encode check; they have no native checks for the hand-written patterns (Python `stellar-xdr` has no high-level forms), except PHP's muxed-ID checks.

## Bugs the current releases still have

These checks fail on the newest releases. Each is a [finding](/project/findings):

- **Python, stellar-sdk 17.0.1:** `scval.to_native` turns string `"b"` and symbol `"b"` into one dict key and drops an entry with no error, the same as [js-stellar-sdk#1789](https://github.com/stellar/js-stellar-sdk/issues/1789). It's open upstream as [StellarCN/py-stellar-base#1250](https://github.com/StellarCN/py-stellar-base/issues/1250), with a fix in review. ([F-0018](/project/findings))
- **Java, java-stellar-sdk 6.0.0:** `Asset.compareTo` orders issuers by strkey text, so decoding the valid pool-share trustline throws, the same as [js-stellar-sdk#1766](https://github.com/stellar/js-stellar-sdk/pull/1766). It's fixed on master by [#832](https://github.com/lightsail-network/java-stellar-sdk/pull/832) but not yet released. ([F-0019](/project/findings))
- **Java and PHP:** a transaction whose `PRECOND_V2` fields are all defaults is rebuilt as `PRECOND_TIME`, so its hash is wrong: `035f2643…` for mainnet transaction `68f96059…`. A wallet that decodes such an envelope and signs it signs a different transaction. New, found by the corpus and filed for both SDKs ([java-stellar-sdk#844](https://github.com/lightsail-network/java-stellar-sdk/issues/844), [stellar-php-sdk#222](https://github.com/Soneso/stellar-php-sdk/issues/222)). ([F-0023](/project/findings), [F-0024](/project/findings))
- **PHP, stellar-php-sdk 1.18.0:** muxed account IDs above 2⁶³ come back negative from `MuxedAccount::getId()` (a real mainnet destination, 18067157809773112502, reads as -379586263936439114), and the decoder accepts 101 operations and a 29-byte memo. New, filed ([stellar-php-sdk#220](https://github.com/Soneso/stellar-php-sdk/issues/220), [#221](https://github.com/Soneso/stellar-php-sdk/issues/221)). ([F-0021](/project/findings), [F-0022](/project/findings))

`kit/check-results.mjs` allows a failure on a current release only when a finding explains it as a known bug with no fixed release yet, and fails if the finding's claim stops being true. When the fixes ship, the pins move and the cells turn green.

The goldens column is the [stellar-core goldens](/corpus/goldens) check: 15,306 frames from core's own test suite, decoded and re-encoded byte for byte. Re-encode and native counts leave out the synthetic fixtures, where they don't apply.

## Earlier JavaScript releases

A passing SDK only proves the corpus raises no false alarms. To show the checks catch real bugs, the JavaScript runner also runs against the releases just before three upstream fixes, and every check that fails there must be explained by a [finding](/project/findings) that links its upstream issue:

<Matrix />

- **17.2.0** orders asset issuers by strkey text (fixed in 17.2.1, [#1766](https://github.com/stellar/js-stellar-sdk/pull/1766)): `TransactionBuilder.fromXDR` throws on the valid pool-share trustline, and map keys don't come out in host order.
- **17.2.1** accepts a muxed ID written as `0x…` and rounds a numeric offer ID above 2⁵³ ([#1785](https://github.com/stellar/js-stellar-sdk/issues/1785)), and silently drops two of the map's ten entries when converting it ([#1789](https://github.com/stellar/js-stellar-sdk/issues/1789)). Both fixed in 17.3.0.

```bash
npm run corpus:js-matrix   # installs each release once into .cache/sdk-js → corpus/results/javascript-matrix.json
```

The releases are listed in `kit/runners/js/versions.json`; `kit/check-results.mjs` fails if a check fails on the current release, if a failure on an earlier one has no finding, or if a finding claims a failure that no release shows.

## Running them

```bash
npm run corpus:js     # @stellar/stellar-sdk   → corpus/results/javascript.json
npm run corpus:go     # go-stellar-sdk         → corpus/results/go.json
npm run corpus:rust   # stellar-xdr (Rust)     → corpus/results/rust.json
npm run setup:python && npm run corpus:python   # stellar-sdk (Python) → corpus/results/python.json
npm run corpus:java   # java-stellar-sdk; jars sha256-pinned from Maven Central → corpus/results/java.json
```

Each result file records the SDK, its exact version, the runtime, and per fixture every check with the differing fields if a check fails.

## What "native" checks, per pattern

| Pattern | Native checks |
|---|---|
| `muxed-payment` | `M…` address, exact muxed ID, base `G…` account, asset, amount |
| `muxed-max-id` | Muxed source and its 2⁵³ + 1 ID, the 2⁶⁴ − 1 destination ID, base accounts, amount; in JavaScript, that non-canonical ID input and an offer ID above 2⁵³ are refused |
| `muxed-soroban-source` | The Soroban transaction's muxed source: base account and ID, the operation |
| `fee-bump` | Outer and inner transaction hashes, fee source, inner source |
| `signed-payload-signer` | `P…` strkey, its ed25519 key, the payload bytes, weight |
| `sac-trust` | Exactly one trustline created in meta, its account, asset and `i64::MAX` limit |
| `pool-issuer-order` | The pool-share operation decodes; the assets compare in network order; the pool ID matches |
| `scmap-host-order` | Entry count and key order survive decoding; the SDK's map sort reproduces host order; native conversion keeps every entry or fails loudly |
| `nested-auth` | Authorization depth and count (walked with the host's depth limit), root contract, the call's return value |
| `memo-non-utf8` | The memo's raw bytes; in JavaScript, that `Memo` and `TransactionBuilder` round-trips keep them |
| `max-length-vectors` | 100 operations, 20 signatures, 20 signers, the thresholds |

## The precision probe

The JavaScript runner also records what `Number()` does to every wide integer in the corpus. It's not a pass/fail check, because the SDK itself is right. It's a measurement of what happens the moment someone's code steps outside it:

| Value | `Number(value)` |
|---|---|
| `1764988090084626463` (muxed ID) | `1764988090084626400` |
| `9007199254740993` (muxed ID, 2⁵³ + 1) | `9007199254740992` |
| `9223372036854775807` (trustline limit) | `9223372036854776000` |
| `18446744073709551615` (muxed ID, 2⁶⁴ − 1) | `18446744073709552000` |

All are off. See [Keep 64-bit integers exact](/guide/wide-integers).

## Adding an SDK

A runner is a few hundred lines: walk `corpus/fixtures`, decode each file by `xdr_type`, re-encode, run the named native checks for the fixture's `pattern`, pass files marked `expect: decode_error` only when they fail to decode, and write `corpus/results/<sdk>.json` in the same shape as the existing ones. Add it to `kit/check-results.mjs` and CI. The Python runner (`kit/runners/python/run.py`) is about 300 lines; the Java one (`kit/runners/java/Run.java`) is a single source file run with `java Run.java`, no build tool.

## Sweeping real traffic

The corpus is chosen to cover every shape; the sweep checks volume. `kit/go/cmd/sweep`, the Rust runner's `sweep` subcommand, `kit/runners/js/sweep.mjs`, `kit/runners/python/sweep.py` and the Java runner's `sweep` mode each read whole ledgers from SDF's public data lake and check two things against stellar-core's own bytes:

- every `LedgerCloseMetaBatch` decodes and re-encodes byte for byte;
- the hash the SDK computes for every transaction in the transaction set is the hash stellar-core recorded for it in the ledger's results.

[`.github/workflows/sweep.yml`](https://github.com/hackcat29/istravex/blob/main/.github/workflows/sweep.yml) runs it on GitHub's runners over a thousand mainnet ledgers spread across the last year and the protocol 30 testnet ledgers; the results are `corpus/results/sweep-<sdk>.json`. The sweep is how the Java hash defect (F-0023) was found: eight mainnet transactions in the corpus's own ledgers whose hash Java gets wrong.

```bash
kit/sweep/fetch.sh pubnet 65400000 65400100 10 /tmp/ledgers
cd kit/go && go run ./cmd/sweep /tmp/ledgers/*.xdr
```
