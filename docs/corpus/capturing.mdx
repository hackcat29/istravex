Two scripts bring real network data into the corpus. Both write fixtures through the same helper (`kit/lib/fixture.mjs`), so every fixture ends up in the same shape regardless of where it came from.

```bash
npm run corpus:capture   # mainnet + testnet + canonical ledgers
```

## Mainnet

`kit/capture/mainnet.mjs` captures transactions by **pinned hash**. Mainnet history never changes, so re-running it reproduces exactly the same bytes.

For each hash it fetches the transaction, its ledger and its operations from Horizon, writes the XDR, and fills `expected_decoded` and `expected_indexed` from **Horizon's JSON**. That separation matters: Horizon is a different codebase from the SDKs under test, so a runner that agrees with the fixture is agreeing with an independent reading of the ledger.

To add a mainnet case, add its hash to the script and read its expectations from Horizon's response. Where Horizon doesn't expose a value (authorization trees, for one), the manifest's `source.expected_from` says where it came from, and all five runners must agree with it.

### Finding the transactions

Rare shapes are rare: you can't page through Horizon looking for a four-level authorization tree. `kit/go/cmd/mainnet-scan` reads mainnet history straight from SDF's public data lake and reports every successful transaction that matches a corpus pattern:

```bash
cd kit/go && go run ./cmd/mainnet-scan -from 65400000 -to 65410000 > candidates.jsonl
```

It needs no keys, no Horizon and no disk: ledgers are streamed and decoded in memory. A laptop is far from the data, so the [**Mainnet scan**](https://github.com/hackcat29/istravex/actions/workflows/mainnet-scan.yml) workflow runs it in 16 shards on GitHub's runners and publishes the merged candidates as an artifact.

The first scan read 400,000 ledgers (about 23 days, ending at ledger 65,483,590):

| Pattern | Candidates on mainnet | In the corpus |
|---|---|---|
| 100 operations in one transaction; 20 signatures | 122,485; 17,268 | [`base-max-length-vectors-pubnet-0001`](/corpus/fixtures) |
| Payments to muxed IDs above 2⁵³ (49,976 above 2⁶³) | 100,999 | [`cap27-muxed-payment-pubnet-0002`](/corpus/fixtures): ID 18,067,157,809,773,112,502 |
| Authorization trees at least three deep (1,358 four deep) | 63,778 | [`cap46-nested-auth-pubnet-0001`](/corpus/fixtures): depth 4, 12 invocations |
| SAC `trust()` calls (CAP-0073) | 5 | [`cap73-sac-trust-pubnet-0001`](/corpus/fixtures): a USDC trustline |
| Memo text that isn't UTF-8, signed-payload signers, Soroban operations from a muxed source, pool issuers out of text order, maps with colliding or mixed keys | 0 | Generated on [pinned stellar-core](/corpus/generating) |

So the corpus takes mainnet data wherever mainnet has it, and generates the rest at mainnet's protocol. Re-run the scan to look further back, or for patterns added later.

## Testnet

Some patterns are valid but rare on mainnet. For those, `kit/capture/testnet.mjs` makes them happen: it funds fresh accounts from friendbot, submits the transactions that produce the pattern, and captures the result through Stellar RPC.

The scenarios themselves live in `kit/capture/scenarios.mjs` and are shared with the [generator](/corpus/generating). The testnet run uses the RPC driver (`kit/capture/drivers/rpc.mjs`), which simulates Soroban transactions to get their footprints and resources, then reads the ledger back with `getLedgers`.

<Note>
Testnet resets periodically, so testnet captures can't be reproduced later by hash. Every run creates *new* cases with new keys. That's why the same scenarios also exist as generated fixtures.
</Note>

## Canonical ledgers

After capturing, `kit/capture/ledgers.mjs` stores the full ledger for every fixture: from the SDF data lake for mainnet, from `getLedgers` for testnet. Then `kit/capture/canonicalize.mjs` rewrites each fixture's meta from the stored ledger, so the fixture is a byte-exact slice of it. [Provenance](/corpus/provenance) explains why.

Stored ledgers are never overwritten unless you pass `--refresh`.

## After capturing

```bash
npm run corpus:run
node kit/check-results.mjs
```

Commit the new fixture directory, its ledger, the updated `corpus/ledgers/index.json` and the results together.
